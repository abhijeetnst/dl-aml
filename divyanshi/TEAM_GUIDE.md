## 1. The project in 30 seconds

> We take sentences that describe correlations between variables ("A correlates with C. However, A is
> independent of B.") and a causal claim ("A directly causes C."), and decide whether the claim follows.
> We do it three ways: a classic ML baseline (AML), a fine-tuned neural model (DistilBERT), and a symbolic
> reasoner that runs the PC causal-discovery algorithm (the oracle). Each system's accepted "X directly
> causes Y" claims become a causal graph per premise. We fit a Bayesian network on each graph and ask
> intervention questions ("if we force A=1, how much does P(E=1) change?"). This shows how errors in text
> extraction turn into wrong answers about interventions.

The dataset is **Corr2Cause** (Jin et al., ICLR 2024, `causalnlp/corr2cause` on Hugging Face). A *premise*
is a closed system of 2–6 variables named A–F. It lists every correlation and every (conditional)
independence. A *hypothesis* is one causal claim. The label says whether the claim follows.

"Neuro-symbolic" means: neural extraction of causal triples from text, then symbolic structure (a DAG),
probabilistic reasoning (a Bayesian network) and do-calculus queries on top.

## 2. Architecture

```
Corr2Cause row: premise + hypothesis
  │
  │  c2c/data.py    (Abhijeet)  load, leakage-safe splits, strict parsers, letter shuffling
  ▼
candidate causal triple (relation, X, Y), relation ∈ {direct, indirect, collider, confounder}
  ├─ c2c/aml.py     (Divyanshi) AML baseline: pattern features → logistic regression
  ├─ c2c/bert.py    (Subham)    fine-tuned DistilBERT → P(valid)
  └─ c2c/oracle.py  (Prashant)  PC skeleton + v-structures → equivalence class → entailed or not
  ▼  P(valid) per triple; one threshold per system, tuned on validation only
c2c/graph.py   (Divyanshi) review gate → one DAG per premise, with provenance → edge metrics
  ▼
c2c/bn.py      (Rahul)     gold DAG + noisy-OR CPDs → simulate 5,000 rows → fit each system's DAG
                           → ATE do-queries, compared with the gold network
  ▼
project1_causal.py / .ipynb  (Abhijeet)  runs every stage, writes results/
```

| Folder / file | What it is |
|---|---|
| `c2c/` | the package: one file per pipeline stage |
| `tests/` | one pytest file per module (25 tests) |
| `project1_causal.py` | notebook source (jupytext). Edit this, never the `.ipynb` |
| `project1_causal.ipynb` | the executed notebook: the main deliverable |
| `results/` | generated by the notebook: metrics CSVs, predictions, DAG figure |
| `review/` | hand-review sheets. The notebook never overwrites them |
| `requirements.txt` | exact pinned versions (Python 3.12) |

**Why it is split this way:** each stage has one input and one output, so each can be tested alone and
owned by one person. Stage outputs are plain data (DataFrames, probability arrays, NetworkX graphs), so the
notebook just wires them together.

## 5. Results and how to talk about them

All numbers are on the official **test** split (1,162 rows, 21 premises). "Shuffled" = same test set
with the variable letters randomly renamed per premise. Labels don't change when you rename letters, so a
system that really reasons should score the same.

| System | Triple F1 | F1, letters shuffled | Edge precision | Edge F1 | mean ATE error test / shuffled |
|---|---|---|---|---|---|
| AML baseline | 0.617 | 0.279 | 0.542 | 0.703 | 0.005 / 0.238 |
| DistilBERT | 0.605 | 0.264 | 0.505 | 0.610 | 0.063 / 0.189 |
| Symbolic oracle | 0.871 | 0.871 | 0.890 | 0.942 | 0.005 / 0.004 |

F1 per relation on test:

| Relation | AML | DistilBERT | Oracle |
|---|---|---|---|
| direct | 0.703 | 0.610 | 0.942 |
| indirect | 0.452 | 0.657 | 0.612 |
| collider | 0.667 | 0.564 | 0.894 |
| confounder | 0.000 | 0.743 | 0.875 |

**The four findings to say out loud:**
1. **The two learned models score about the same (~0.61 F1) and the symbolic oracle is far ahead (0.87).**
   DistilBERT is better on indirect causes and confounders; AML is better on direct edges and colliders.
2. **Most of the learned models' score is a shortcut.** The dataset generator names causes before effects
   in alphabetical order, so "B directly causes A" is never true. Shuffle the letters and both learned
   models collapse to ~0.27. The oracle doesn't move, because logic doesn't care about names.
3. **Graph errors become intervention errors.** Extra edges cost little, because the fitted network learns
   that they carry no effect. Missing or reversed edges cost a lot: where DistilBERT missed every edge of a
   premise, it answers "no effect" when the true effect is +0.43.
4. **The dataset has label noise.** The oracle disagrees with 44 of 1,162 test labels (96.2% agreement).
   We audited 10: 5 labels contradict every graph consistent with the premise, and 5 use a looser meaning of
   "indirect cause".

## 6. Questions anyone on the team might get (with answers)

**Q: What is the deep learning part and what is the AML part?**
DL: DistilBERT fine-tuned as a sequence-pair classifier (`c2c/bert.py`). AML: logistic regression on
hand-designed structural features (`c2c/aml.py`). Both see the same 30,000 training rows, so the comparison
is fair.

**Q: Why not train on all 205k rows?**
Compute budget: 30k rows × 2 epochs already takes ~1.5 h on an M3 Pro laptop GPU. Both models use the same
subset (seed 0).

**Q: How do you know you didn't overfit to test?**
Thresholds and every design choice were tuned on validation only. We also found that the official splits
leak (3 validation premises appear in test, 2 in train) and removed them, keeping test untouched.

**Q: What is a DAG, a Bayesian network, and an intervention?**
DAG: directed graph with no cycles, an arrow X→Y meaning "X directly causes Y". BN: a DAG plus one
probability table per variable given its parents. Intervention do(X=x): force X to a value, which cuts the
arrows into X, then see how Y's distribution changes. ATE = P(Y=1 | do(X=1)) − P(Y=1 | do(X=0)).

**Q: Why simulate data instead of using real data?**
The variables are just letters; there is no real-world data for them. We put known, strong effects on the
gold graph (noisy-OR), simulate from it, and fit each system's graph on the same rows. ATE errors then
measure only how good each system's *structure* is.

**Q: If the oracle is so good, why build ML models?**
The oracle only works because Corr2Cause text follows 5 fixed sentence patterns we can parse exactly. Real
text doesn't, so you need learned extractors. The oracle shows the ceiling and exposes the shortcut.

**Q: Why is the oracle's F1 not 1.0?**
Label noise (see finding 4) and a different definition of "indirect cause". Under a looser definition
("a directed path of length ≥ 2") it agrees with 99.2% of indirect-cause labels. We kept our definition
because validation didn't support switching, and we don't make choices based on test.

**Q: How do we reproduce everything?**
`pip install -r requirements.txt`, `pytest -q` (25 tests), `python -m c2c.bert` once (~1.5 h), then run
the notebook. It re-executes with identical results; all seeds are fixed.

## 7. Limitations (say these before someone else does)

- Small test set: 21 premises, 13 with gold edges; intervention queries use 5 premises (76 queries per set).
- 37.7% of training pairs are longer than 512 tokens, so DistilBERT sees a truncated premise.
- The gold graph contains only the edges the dataset labels as direct causes.
- CPDs are synthetic, so ATE errors test graph structure, not the real world.
- The review gate (cycle breaking, conflicting directions) never fired on this data: the text models only
  propose earlier-letter → later-letter edges, which can't form cycles. Unit tests show that it works.
- `review/` draft verdicts were derived from each premise's independence statements with the oracle's own
  reasoning, so they aren't independent of it. They count as a human review only after we fill the
  `team_verdict` column.
